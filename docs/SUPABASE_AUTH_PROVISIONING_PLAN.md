## 4B. Recovery-Delivery Policy for Provider-Rejected Domains (6C-FIX2, 2026-08-14)

**Observed production failure (run `AP-20260814093703`):** `A4EI9QVE` (trainer, `t***@gym.com`) — user CREATION **succeeded** (target `78f1d8d8-89a8-47d4-b8bb-9fcf0f798db1`), but recovery-link delivery failed: `POST /auth/v1/recover` → `Email address "trainer@gym.com" is invalid` (GoTrue `ErrorCodeEmailAddressInvalid`, HTTP 400).

**Root cause (confirmed, not assumed):** GoTrue validates email addresses at **email-SEND time** (`internal/api/mail.go` → `sendEmail` → mailer `validateclient`: `ErrInvalidEmailAddress`/`ErrInvalidEmailFormat`/`ErrInvalidEmailDNS` → `"Email address %q is invalid"`). Supabase's own error-code reference documents `email_address_invalid` as: *"Example and test domains are currently not supported."* The admin **create** endpoint does not send mail (created with `email_confirm: true`), so creation succeeds; only `/recover` (and any other email send) hits the stricter validator. DNS probes showed `gym.com` has MX + A records — the rejection is the validator's domain policy, not a "no MX" rule. The source email is RFC-valid and accepted by Firebase; **no email is fabricated or rewritten**.

**Scope:** the approved set contains 2 affected addresses (`trainer@gym.com` = A4EI9QVE, `member@gym.com` = fvPn9yyf). Other non-allowlisted domains (`example.com`, `mrworlds.com`, `doefy.com`) may hit the same send-time policy — the provisioner classifies per-user, so any affected user is handled identically.

**Approved policy (Option A — supported by evidence):** the user is **kept created** (never rolled back, never deleted). Recovery-link delivery is **separated from creation**; a delivery failure is classified **`RECOVERY_DELIVERY_FAILED`** and the run continues. The affected users require **manual credential setup/recovery** (e.g., Supabase Dashboard → Auth → user → reset/manual password) by the gym owner. Creation-time rejections (an address invalid at `POST /admin/users`) are classified **`MANUAL_REVIEW`** — no user created, no fabricated address, run continues.

**Resume behavior:** re-running the provisioner skips existing-correct users (idempotent), never duplicates, never deletes, never overwrites unrelated metadata; `--resend-recovery` (execution only) re-attempts recovery delivery for existing-correct normal users. Rejected users stay banned; recovery is never attempted for them. Firebase password hashes/salts are NEVER migrated (temporary passwords in memory only).

## 5. Supabase Auth Provisioning Model (intended, NOT executed)

- **API**: Supabase GoTrue Admin API — `POST {SUPABASE_URL}/auth/v1/admin/users` with `apikey` + `Authorization: Bearer <service_role>` headers (server-side only, at execution time).
- **ID model**: `auth.users.id` = **new GoTrue-generated UUID**. Firebase UID is **never** forced into `auth.users.id`. Firebase UID is preserved separately in `profiles.firebase_uid`; `profiles.id` = the new auth user UUID (satisfies FK 0001:92). The deterministic-UUID scheme previously planned for `profiles.id` is **superseded** by this model (schema FK requirement); deterministic UUIDs remain in use for other tables (subscriptions, plans, etc.) where no FK to `auth.users` exists.
- **Email**: original Firebase email is used verbatim (verified valid, unique per §4).
- **Confirmation**: `email_confirm=true` at creation; user metadata carries `{ firebase_uid, role, gym_id }` (redundant copy for traceability; the authoritative fields live on `profiles`).
- **Rejected users**: created as normal auth users (FK requirement), then **banned** via `banned_until` (far future) — sign-in impossible — mirroring `profiles.account_disabled=true` (D1.1 "approved disabled semantics"). A later explicit decision can hard-delete banned rows.
- **Gym owners / pending / members / trainers**: active users with forced reset (§6).
- **Conflicts with approved decisions (task 5)**: 0 role/gym conflicts found. The 11 duplicate-email users are the only deviation, and they are *blocked*, not imported against policy.

## 6. Temporary-Password & Forced-Reset Strategy

- **Temporary password**: per-user random 16-char (A-Za-z0-9, no ambiguous chars) generated **at execution time only**, passed directly to the Admin API create call, **never written to files, manifests, logs, or docs**. If passwordless email-confirmation is enabled in the project, prefer the passwordless path (recovery link only).
- **Forced reset**: (a) primary — `email_confirm=true` + immediate recovery-link email per user (`POST /auth/v1/recover`), so the first sign-in goes through a reset link; (b) fallback — temp password with the app-level "change password on first login" flag stored on `profiles` (no schema change; app-enforced). All users created active are forced through one of these paths.

## 7. Security Requirements

- NEVER store/print/log: temp passwords, Firebase UIDs-only mapping is allowed (they are opaque), real emails (masked everywhere), access tokens, service-role keys.
- Emails appear in artifacts **only** as `f***@domain` masks + validity/duplicate flags. Full unmasked identities exist solely inside the source Firebase docs (never exported).
- No password material of any kind is read, exported, transformed, or reused (password, passwordHash, password_hash, salt, passwordSalt, Firebase Auth hashes) — enforced by the DENY_KEY scan (GATE A) and the read-only script which fetches only the `users` collection transform set.
- Execution credential must come from environment variables at run time — never embedded in source, `.env*` committed files, or docs.
- Admin API calls happen only over TLS with the service-role key; the key is never used from the browser (app continues to use the anon/publishable key + RLS).
- Rejected/banned users must not receive reset links.
- Idempotency: execution queries `auth.users` by email first; existing users are reported as conflicts (never overwritten, never deleted).
